# 스타 자료 (나무위키 덤프)

스타 추천 답변에 쓸 프로필 자료를 나무위키 덤프에서 뽑습니다. 이 문서는 자료의 출처와 이용 조건, 덤프에서 무엇을 고르는지, 추출 스크립트를 실행하는 방법을 정리합니다.

## 출처

- 나무위키 (https://namu.wiki) 문서
- 덤프 파일: `yourwiki-namumark-20260829-build20261002` (2026-08-29 크롤링)
  - 배포처: https://huggingface.co/datasets/iamtalker/yourwiki-namumark-20260829
  - 나무위키 운영사가 낸 공식 덤프가 아닙니다. archive.org 에 있는 크롤링을 나무마크로 되돌린 비공식 복원본입니다.
  - 압축을 풀면 약 30GB 짜리 JSON 배열 하나이고, 줄바꿈이 없습니다. 레코드 형태는 `{"namespace", "title", "text", "contributors", "last_modified", "source"}` 입니다.
- 원저작자: 나무위키 기여자. 문서별 기여 이력은 `https://namu.wiki/history/<문서 제목>` 에서 볼 수 있습니다.

## 라이선스

나무위키 문서는 **CC BY-NC-SA 2.0 KR** 입니다 (https://creativecommons.org/licenses/by-nc-sa/2.0/kr/).

- **비영리**: 영리 목적으로 쓸 수 없습니다. 이 서비스는 비영리로만 씁니다. 상업적으로 쓰게 되면 이 자료는 쓸 수 없습니다.
- **출처 표시**: 자료를 보여 줄 때 나무위키 출처와 문서 링크를 밝히고, 원문을 정제·발췌했다는 사실을 함께 적습니다.
- **동일조건 변경허락**: 추출 결과와 이를 가공한 자료도 같은 라이선스를 따릅니다.

저장소 규칙:

- 원본 덤프와 추출 결과는 저장소에 올리지 않습니다. 기본 출력 위치인 `data/namu/` 는 `.gitignore` 에 넣었습니다.
- 테스트용 샘플 `tests/fixtures/namuwiki/namu_sample.json` 은 문서 14건을 1,500자 이하로 자른 발췌본입니다. 출처와 라이선스를 적은 `namu_sample.LICENSE.txt` 를 항상 옆에 둡니다.

## 무엇을 고르는지

분류(`[[분류:...]]`)만 보고 고릅니다. 본문 정제와 프로필 추출은 적재 단계(아래 "정제·청킹·DB 적재")에서 합니다.

1. **문서 범위**: 제목에 `분류:`, `틀:`, `나무위키:` 같은 접두어가 없는 일반 문서만 봅니다. 덤프의 `namespace` 값은 전부 0이라서 제목 접두어로 구분합니다.
2. **분류 확장**: 유명한 스타 문서에는 `[[분류:나연]]` 처럼 자기 이름 분류 하나만 있는 경우가 많습니다. 실제 분류(한국 여가수, 출생연도, 소속 그룹 등)는 `분류:나연` 문서에 있으므로, 문서에 자기 이름 분류가 있으면 그 분류 문서의 상위 분류를 한 단계 더합니다. 분류 문서의 `== 하위 분류 ==` 이후 목록과 `[[분류:X|Y]]` 형태의 링크는 상위 분류로 보지 않습니다.
3. **그룹**: `대한민국의 걸그룹`, `보이그룹`, `혼성그룹`, `힙합 그룹`, `보이밴드그룹` 분류가 있는 문서입니다.
4. **인물**: 아래 신호가 하나 이상 있어야 합니다.

   | 신호 | 내용 |
   | --- | --- |
   | S1 | 한국 연예 직업 분류 (한국 여가수, 대한민국의 영화배우, 트로트 가수 등) |
   | S2 | 아이돌 역할 분류 (아이돌 보컬·댄서·래퍼·리더·센터). 나라 구분이 없어서 한국인 근거가 따로 필요합니다 |
   | S3 | 그룹 문서 이름 분류 또는 `<그룹>/멤버` 분류 |
   | S4 | 한국 연예 기획사의 `소속 아티스트` 계열 분류. 데뷔연도 분류가 같이 있을 때만 인정합니다 |
   | S5 | `인터넷 밈/가수/대한민국` 등. 한국인 근거로만 쓰고, 이것만 있으면 넣지 않습니다 |
   | S6 | 방송사 연예대상 수상자, `출신 방송인` 등 예능인 분류 |

   그리고 다음 경우는 뺍니다.
   - 출생연도 분류가 없고 음반·노래·방송 프로그램·팬덤·콘서트 같은 분류가 있는 문서 (인물이 아님)
   - 한국인 근거(S1, S3~S6, 본관 분류)가 없는 문서 (주로 일본 아이돌)
   - S1 없이 외국 가수·배우 분류만 있는 문서
   - 방송인·모델·댄서 같은 약한 직업 분류만 있으면서 운동선수·정치인·아나운서 등 다른 직업 분류가 있는 문서 (단, 연예대상·고정 출연진 같은 예능 근거가 있으면 남김)
5. **하위 문서**: `아이유/여담` 처럼 고른 인물·그룹 제목 뒤에 `/` 가 붙은 문서입니다. 따로 저장하고 부모 제목을 같이 적습니다.
6. **별칭**: 고른 인물·그룹·하위 문서를 가리키는 리다이렉트입니다 (예: `갓세븐` → `GOT7`).

동명이인이 많아서(`김동현` 등) 키는 괄호를 포함한 전체 제목으로 씁니다.

`NNNN년 데뷔` 분류는 운동선수에게도 붙어서 포함 신호로 쓰지 않습니다. 개요 첫 줄로 직업을 다시 확인하는 단계는 없습니다.

## 실행 방법

저장소 루트에서 실행합니다. 표준 라이브러리만 씁니다.

```bash
python -m scripts.namuwiki.extract --dump <덤프 JSON 경로> --out data/namu
```

| 옵션 | 설명 |
| --- | --- |
| `--dump` | 압축을 푼 덤프 JSON 파일 |
| `--out` | 결과를 쓸 폴더 |
| `--chunk-mb` | 한 번에 읽을 크기(MiB, 기본 16) |
| `--max-record-mb` | 이보다 긴 레코드는 건너뜀(2^20 글자 단위, 기본 64). 덤프에 수억 글자짜리 손상 레코드가 있어서 둡니다 |
| `--known-group` | 입력에 그룹 문서가 없을 때 S3 판단에 쓸 그룹 제목 (여러 번 지정 가능) |
| `--quiet` | 진행 로그를 끔 |

덤프 전체를 메모리에 올리지 않습니다. 파일을 조금씩 읽어 레코드를 하나씩 풀고, 두 번 읽습니다.

1. 모든 레코드의 제목·리다이렉트·분류와 분류 문서의 상위 분류를 모아 규칙을 적용합니다.
2. 고른 문서의 원문을 JSONL 로 씁니다.

출력 파일 (한 줄에 JSON 객체 하나, UTF-8):

| 파일 | 필드 |
| --- | --- |
| `persons.jsonl` | `title`, `kind`(`person`), `signals`, `categories`, `text` |
| `groups.jsonl` | `title`, `kind`(`group`), `categories`, `text` |
| `subdocs.jsonl` | `title`, `kind`(`subdoc`), `parent`, `parent_kind`, `categories`, `text` |
| `aliases.jsonl` | `title`, `kind`(`alias`), `target`, `categories`(빈 목록), `text` |
| `stats.json` | 읽은 레코드 수, 규칙별 제외 수, 파일별 건수 |

`text` 는 나무마크 원문 그대로입니다. `categories` 는 자기 이름 분류를 확장한 뒤의 분류입니다(하위 문서는 문서에 적힌 분류).

## 정제·청킹·DB 적재

추출 결과(`data/namu/`)를 평문으로 정제하고, 프로필 항목을 뽑고, 문단 조각으로 나눠 PostgreSQL 의 `star_profiles`, `star_chunks` 테이블에 넣습니다. 테이블 구조는 `docs/DATABASE.md` 에 있습니다.

```bash
python -m scripts.namuwiki.load --input data/namu --database-url "$DATABASE_URL"
```

| 옵션 | 설명 |
| --- | --- |
| `--input` | `scripts.namuwiki.extract` 의 출력 폴더 |
| `--database-url` | PostgreSQL 주소. 생략하면 환경 변수 `DATABASE_URL` |
| `--limit` | 앞에서부터 스타 N건만 넣음 (그룹 → 인물 순서). 확인용 |
| `--batch` | INSERT 한 번에 보낼 행 수 (기본 1000) |
| `--content-index` | 조각 본문(`star_chunks.content`) 검색 인덱스. `none`(기본) 또는 `trgm` |
| `--quiet` | 진행 로그를 끔 |

- 실행할 때마다 두 테이블을 비우고 다시 채웁니다. 전체가 트랜잭션 하나라서 중간에 실패하면 이전 데이터가 그대로 남습니다. 적재하는 동안에는 두 테이블을 읽는 쿼리가 기다립니다.
- 테이블이 없으면 만듭니다. `pg_trgm` 확장은 `CREATE EXTENSION IF NOT EXISTS` 로 시도하고, 권한이 없으면 `simple` 전문 검색 인덱스로 대신합니다.
- 인덱스는 이름 검색용(`title`, `aliases`)과 조건 검색용(`kind`·`gender`, `debut_year`, `birth_year`)만 기본으로 만듭니다. 크기가 작습니다.
- 조각 본문 인덱스는 `--content-index trgm` 을 줄 때만 만듭니다. 전체 덤프에서 이 인덱스 하나가 299MB 로 테이블(234MB)보다 커서 기본값에서 뺐습니다. 채팅 검색은 출생지·성별·데뷔연도 같은 조건으로 먼저 스타를 추린 뒤 그 스타들의 조각만 훑기 때문에 본문 인덱스 없이도 빠릅니다(아래 "채팅 검색" 참고).
- 오류가 나도 DB 주소나 드라이버 메시지는 출력하지 않습니다(비밀번호가 들어 있을 수 있어서).

### 정제 규칙 (`clean.py`)

| 대상 | 처리 |
| --- | --- |
| `[[분류:…]]`, `[[파일:…]]`, `[include()]`·`[youtube()]` 같은 매크로, `[목차]`, `[각주]` | 삭제 |
| 각주 `[* …]` | 괄호 짝을 맞춰 통째로 삭제 |
| `[[대상\|표시]]`, `[[대상]]` | 표시 글자 또는 대상 이름만 남김. 외부 링크(`http…`)는 삭제 |
| `{{{#fff 글}}}`, `{{{+1 글}}}`, `{{{#!wiki …}}}` | 안쪽 글만 남김. `#!html`, `#!syntax` 블록은 삭제 |
| `'''굵게'''`, `''기울임''`, `__밑줄__` | 기호만 제거. `~~취소선~~`, `--취소선--` 은 내용째 삭제 |
| `[br]`, `<br>` | 줄바꿈 (표 칸 안에서는 ` / `) |
| 표 | 칸 속성을 지우고 2칸 행은 `라벨: 값`, 나머지는 ` \| ` 로 이음 |
| 첫 `==` 제목 이전 | 버림 (내비게이션 상자와 인포박스. 인포박스는 프로필로 따로 저장) |
| `(데뷔일로부터 +N일)`, 날짜 뒤 `(34세)` | 크롤링 시점에 고정된 값이라 삭제 |
| 편집 보호 안내, "…문서를 참고하십시오" 같은 줄 | 삭제 |

본문 속 표는 ` | ` 로 이은 평문이 되고, 원문 괄호 짝이 맞지 않는 링크 일부는 글자만 남습니다.

### 프로필 항목 (`profile.py`)

인포박스(첫 제목 전의 2칸 표 행)와 분류에서 뽑습니다. 둘 다 있으면 분류를 먼저 씁니다.

| 항목 | 방법 |
| --- | --- |
| 성별 | `한국 남가수`·`한국 여배우` 같은 분류, 소속 그룹이 걸그룹(여)·보이그룹(남)인지. 서로 다르면 비움 |
| 출생연도 | `NNNN년 출생` 분류, 없으면 인포박스 `출생` |
| 소속 그룹 | 그룹 문서 이름 분류 또는 `<그룹>/멤버` 분류, 없으면 인포박스 `소속그룹` |
| 데뷔연도 | `NNNN년 데뷔` 분류, 없으면 인포박스 `데뷔` |
| 출생지 | 인포박스 `출생` 에서 날짜가 아닌 부분, 없으면 `X 출신 인물` 분류 |
| 소속사 | 인포박스 `소속사`(또는 `소속`)의 첫 값. `없음`, `???` 같은 값은 비움 |
| 키 | 인포박스 `신체`·`키` 의 `NNNcm`. 120~230 밖이면 비움 |
| 다른 이름 | 괄호를 뺀 제목, 본명, 예명, 이 문서를 가리키는 리다이렉트 제목 (30자 이하이고 `/`, `!`, `?`, `,` 가 없는 것) |

인포박스 행은 `프로필` 이라는 첫 조각으로도 저장합니다. 단 `가족`(가족 실명·생년월일)과 `거주지`(동 단위 주소) 행은 넣지 않습니다. 외모(안경, 머리 모양 등)는 정해진 칸이 없어서 뽑지 않았고, 본문 조각 검색으로 찾아야 합니다.

### 청킹 (`chunk.py`)

- `== 제목 ==` 으로 섹션을 나누고, 섹션 안에서 빈 줄 기준 문단을 500~1000자로 모읍니다.
- 1000자보다 긴 문단은 문장 끝(`다.`, `요.` 등)에서 자르고, 그래도 길면 1000자에서 자릅니다. 모든 조각은 1000자 이하입니다.
- 짧은 섹션은 다음 섹션과 합치고, 합친 섹션 제목은 본문 안에 `[여담]` 처럼 적습니다.
- `둘러보기`, `관련 문서`, `같이 보기`, `외부 링크`, `각주` 섹션은 버립니다.
- 하위 문서(`아이유/여담`)는 부모 스타의 조각으로 이어 붙이고, 섹션 앞에 하위 문서 이름을 붙입니다(`여담 > 습관`). 직캠·응원법·음반 목록·광고·화보·논란·사건 사고처럼 목록 위주이거나 덩치가 큰 하위 문서는 넣지 않습니다.

### 출처와 라이선스 저장

- 스타와 조각마다 `source_url` 에 원문 주소(`https://namu.wiki/w/<제목 URL 인코딩>`, 하위 문서의 `/` 는 그대로)를 저장합니다.
- 라이선스 문구는 행마다 넣지 않고 두 테이블의 테이블 주석(`COMMENT ON TABLE`)과 이 문서에 둡니다. 챗봇이 이 자료로 답할 때는 출처 링크와 `CC BY-NC-SA 2.0 KR`, 나무위키 문서를 정제·발췌했다는 사실을 같이 보여 줘야 합니다. 채팅 답변에는 검색 결과를 썼을 때 서버가 `출처: 나무위키(CC BY-NC-SA 2.0 KR) - 이름1, 이름2` 줄을 붙입니다. 문서 링크는 AI 에 넘기는 참고 자료에만 들어 있고 답변 화면에는 아직 링크로 보여 주지 않습니다.

### 덤프 빌드 20261002 적재 결과

로컬 Docker `postgres:16` 에 위 명령을 그대로 돌린 결과입니다 (단일 프로세스, 낮은 CPU 우선순위).

| 항목 | 값 |
| --- | ---: |
| `star_profiles` | 20,692행 (인물 19,138 · 그룹 1,554) |
| `star_chunks` | 179,464행 (하위 문서 4,832건 포함, 5,636건은 제외 규칙으로 뺌) |
| 조각 길이 | 평균 620자, 중앙값 641자, 최대 1000자 |
| `star_chunks` 크기 (`pg_total_relation_size`, 기본 `--content-index none`) | 249MB (테이블 234MB + 인덱스 약 10MB) |

| `star_profiles` 크기 | 약 10MB (이름 `pg_trgm` 인덱스 2개 약 4.6MB, 조건 검색 인덱스 3개 0.5MB 포함) |

인물 19,138명 중 값이 들어간 수: 성별 18,133 · 출생연도 17,870 · 데뷔연도 14,416 · 키 12,755 · 출생지 11,452 · 소속사 10,597 · 소속 그룹 4,750.

본문 `pg_trgm` 인덱스는 테이블보다 커서 기본으로 만들지 않습니다. 조건 없이 단어만으로 전체 본문을 찾는 검색이 꼭 필요해지면 `--content-index trgm` 으로 다시 적재합니다.

## 채팅 검색

채팅 API 는 질문마다 이 두 테이블을 검색해 결과를 AI 시스템 프롬프트의 `<참고자료>` 블록으로 넘깁니다(`backend/app/services/star_search.py`). 규칙 기반이고 AI 를 쓰지 않습니다. 채팅 요청·응답 형식은 [API 명세](API.md#post-apichat)에 있습니다.

| 질문 속 표현 | 조건 |
| --- | --- |
| `부산`, `서울`, `경기도`, `경상도`, `수원` 같은 시·도와 주요 도시 | 출생지가 그 지역으로 시작 |
| `남자`·`남성`·`보이그룹`, `여자`·`여성`·`걸그룹` | 성별 (`M`/`F`) |
| `아이돌`·`멤버`·`걸그룹`·`보이그룹` | 소속 그룹이 있는 인물 |
| `배우`, `가수` | 프로필 조각(인포박스)의 직업 등에 그 단어가 있음 |
| `2020년 데뷔`, `00년생`, `90년대생` | 데뷔연도, 출생연도 |
| `키 큰`, `키 작은` | 키가 있는 스타만, 키 순서로 정렬 |
| 그룹·스타 이름 (`트와이스`, `아이유`) | 제목이나 다른 이름과 정확히 같을 때. 그룹이면 멤버 목록, `비슷한` 이 있으면 성별·분야·데뷔 시기가 비슷한 스타 |
| 나머지 단어 (`안경`, `보조개`) | 위 조건으로 추린 스타(최대 300명)의 조각에서만 찾음 |

- 조건이 하나도 없고 이름도 아니면 단어만으로 전체 조각을 찾되 40건에서 멈춥니다. PostgreSQL 에서 150ms 를 넘기면 못 찾은 것으로 보고 `star_search_fallback_timeout` 을 남깁니다.
- 조건이 없는 짧은 후속 질문(`그 중에 보조개 있는 사람`)은 바로 앞 질문의 조건을 이어받습니다.
- 결과는 최대 5명이고, 스타마다 주요 프로필 항목과 300자 안팎의 발췌 2개, 원문 주소를 담아 시스템 프롬프트 끝에 `<참고자료>` … `</참고자료>` 블록으로 붙입니다. 나무위키는 누구나 고칠 수 있는 문서라서 발췌·제목·다른 이름·섹션 이름에 이 태그(띄어 쓴 변형 포함)가 들어 있으면 지우고 넣어, 블록이 중간에 닫히지 않게 합니다. 찾지 못한 단어는 `자료에서 찾지 못한 조건` 으로 함께 알려 줍니다.
- 결과가 있으면 서버가 답변 끝에 `출처: 나무위키(CC BY-NC-SA 2.0 KR) - 이름1, 이름2` 줄을 붙입니다. 이름은 답변에서 언급한 스타만 넣고(제목, 다른 이름, 괄호를 뺀 제목으로 비교), 아무도 언급하지 않았으면 검색된 스타를 모두 넣습니다. 모델이 직접 쓴 출처 줄은 지우고, 이 줄까지 포함해 저장합니다. AI 에 이전 대화를 보낼 때는 이 줄을 뺍니다. 결과가 없으면 붙이지 않고 시스템 프롬프트도 기본 그대로입니다.
- 스타 테이블이 없거나 비어 있거나 DB 오류가 나도 채팅은 그대로 동작합니다(참고 자료 없이 답변). PostgreSQL 에서는 검색 쿼리마다 250ms 제한을 둡니다.
- 출생지·성별·데뷔연도·출생연도·키·아이돌 여부(소속 그룹 유무)는 `star_profiles` 열로 거릅니다. 배우·가수 구분은 열이 없어서 프로필 조각(인포박스 `직업` 등)에 그 단어가 있는지로 봅니다.
- `안경`, `보조개` 같은 외모 단어는 정해진 칸이 없어서, 조건으로 추린 스타(최대 300명, 문서가 긴 순)의 조각에서만 `LIKE` 로 찾습니다. 그래서 본문 인덱스가 없어도 됩니다.
- PostgreSQL 에서는 조각 조회가 `(profile_id, chunk_index)` 인덱스를 타도록 그 쿼리에서만 `enable_seqscan` 을 끕니다. 그대로 두면 플래너가 조각 테이블 전체(234MB)를 읽어 250ms 넘게 걸렸습니다.

전체 적재(본문 인덱스 없음) 뒤 로컬 Docker `postgres:16` 에서 같은 질문을 5번씩 돌린 결과입니다 (`search_stars` 함수만 호출, AI 호출 없음).

| 질문 | 찾은 스타 | 첫 실행 | 중앙값 |
| --- | ---: | ---: | ---: |
| 안경 쓴 부산 출신 아이돌 추천해줘 | 5 | 71ms | 42ms |
| 2020년에 데뷔한 걸그룹 멤버 중에 키 큰 사람 | 5 | 7ms | 6ms |
| 아이유랑 비슷한 가수 | 5 | 24ms | 21ms |
| 보조개 있는 남자 배우 | 5 | 106ms | 94ms |
| 트와이스 멤버 알려줘 | 5 | 21ms | 18ms |
| 조건 없이 단어 하나 (전체 조각에서 못 찾는 경우) | 0 | 160ms | 160ms |

결과를 눈으로 본 한계:

- `배우`·`가수` 구분이 거칠어서 `보조개 있는 남자 배우` 에 연기도 하는 아이돌(황민현, 옹성우 등)이 나오고, `아이유랑 비슷한 가수` 에 치어리더 문서(박기량)가 섞였습니다.
- 단어가 들어 있기만 하면 맞은 것으로 봅니다. `안경` 은 "손 안경 포즈" 같은 문장에도 걸립니다.
- 조건에 맞는 사람이 많으면 문서가 긴 순으로 300명만 봅니다. 그 밖의 스타는 단어가 있어도 나오지 않습니다.

테스트는 저장소 루트에서 `pytest -q tests/namuwiki` 로 돌립니다. 실제 덤프 없이 샘플만 씁니다. 적재 테스트는 SQLite 메모리 DB 를 쓰고, `TEST_POSTGRES_URL` 이 있으면 PostgreSQL 에 임시 스키마를 만들어 실제로 적재해 봅니다.
